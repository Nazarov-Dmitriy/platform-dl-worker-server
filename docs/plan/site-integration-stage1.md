# Задание для интеграции бэкенда и фронтенда сайта

Дата: 2026-10-13. Результат этапа 1 worker-server. Это задание на будущие изменения
serverBreasts/front; в этом этапе их код, production, .env и рабочие задания не изменялись.
Обновление 2026-10-13: диспетчер, обработчик и FILE-видеопуть реализованы локально.
Интеграция сайта по B1–B5 ещё требуется. Перед началом свериться с
[текущим аудитом готовности](../audits/readiness-review-2026-10-13.md).

## Что передать агенту

Передать этот файл вместе с каталогом [contracts](../../contracts/README.md),
[аудитом](../audits/site-backend-2026-10-13.md) и
[общим планом](worker-plan.md). Читать protocol.md и states.md вместе со схемами:
JSON Schema описывает форму, нормативные документы — порядок действий и проверки.

Работать в отдельной ветке сайта. Сначала проверить инструкции его репозитория,
найти фактические точки интеграции, затем изменить код и проверить тестами.
Не запускать production-миграции, удаления, restore или реальные задания для проверки.
Новые режимы до общей приёмки выключены; локальный SERVER продолжает работать.

## Подтверждённая исходная точка

- LessonVideoProcessingService.processMainVideoAsync и ChannelPostVideoProcessorImpl.process
  вызывают локальную упаковку через общий HlsPackagingServiceImpl, а не media.transcode.
- Клиент внешних заданий и локальная очередь уже существуют. Сохранить устойчивый UUID,
  снимок заявки и обработку неопределённого ответа; адаптировать DTO, а не дублировать очередь.
- Старый MediaTranscodeJobHandler принимает одно quality с умолчанием P720 и фиксированные
  outputs/ZIP. Это не реализация v2 и не пример полного профиля результата.
- Ручные VTT/SRT урока и текст расшифровки уже есть. Автоматическое создание/перевод
  субтитров, каталог возможностей и частичные результаты требуют новой интеграции.
- Проверка production runtime остаётся отдельной задачей перед запуском.

## Бэкенд: порядок изменений

### B1. Клиент v2 и долговечное состояние

Добавить версионированные DTO и HTTP-клиент из OpenAPI/JSON Schema. В новом режиме
использовать /api/v2/site, не отправлять v2 в legacy /api/site/jobs.
Старые активные записи не переотправлять автоматически новым UUID: подготовить явный
переход и сверку. Legacy dispatcher отвечает PROTOCOL_UPGRADE_REQUIRED, а не исполняет ZIP.

Хранить UUID, ревизию загрузки, неизменяемый запрос и hash, последнее состояние/revision,
Fence и Artifact, transfer request IDs, publication claim, releaseReceipt и outbox.
В повторе HTTP тело и UUID сохраняются. Таймаут/5xx не запускают параллельный резерв.
Повтор после неопределённого ответа проверяет прежнюю работу; явный отказ до приёма
отличать от неопределённости и от окончательной ошибки уже принятого задания.

### B2. Продуктовые пути урока и канала

Встроить создание media.transcode в обе загрузки. Передавать полный Profile из Settings → Media:
выбранные качества, длительность сегмента, preset/CRF, аудио, битрейты и допуск COPY.
Снимок не меняется при последующей настройке сайта. Не подменять список качеств P720.
Политику COPY/ENCODE/SKIP_UPSCALE сохранить из общего HlsPackagingServiceImpl.
encoderPolicy=X264_EXACT по умолчанию; аппаратный путь включать только после проверки
соответствия настройкам. Исходник низкого разрешения не увеличивать искусственно.

Исходник должен находиться в доступном хранилище до принятия внешней работы:
путь в локальной временной папке сайта обработчику недоступен. Зафиксировать ревизию,
size/hash и роль UPLOAD. Для дополнительной операции над опубликованным медиа использовать
PUBLISHED_MEDIA; её ошибка не удаляет исходное опубликованное видео/аудио.

### B3. Поллер и временные ссылки

Опрос заданий и transfer requests — сервером сайта, с durable cursor/повторами.
SOURCE выдаёт свежие GET для той же ревизии и Fence. UPLOAD выдаёт PUT для проверенного
динамического manifest, а не заранее фиксированные outputs. Страницы grants идемпотентны.
Ссылки обновляются и после принятия заявки, не только при первоначальном POST.

Объекты попытки изолировать по site/job/dispatcherEpoch/generation/assignmentId.
Никогда не разрешать процессору писать в окончательный опубликованный prefix.
Ограничить размер/число/пути объектов по контракту; источник, staging и финальные
объекты должны принадлежать этому сайту и конкретной ревизии продукта.
Не передавать постоянные S3 credentials и не пересылать медиа через диспетчер.

### B4. Проверка и публикация

AWAITING_PUBLICATION означает готовность пакета к проверке, не READY продукта.
Проверить реальные объекты, размеры/checksums, m3u8 и все их локальные ссылки,
выбранные фактические качества и успешный основной шаг. ETag не равен SHA256.

Получить publication-claim: он фиксирует артефакт в PUBLISHING и исключает отмену/резерв.
Затем скопировать staging в защищённый final prefix и проверить уже скопированные файлы.
В одной транзакции сайта проверить ревизию продукта, записать READY/дорожки и outbox PUBLISHED.
Outbox повторять до PublicationAck. Если до READY проверка окончательно неудачна,
после получения claim отправить REJECTED с причиной. После READY отправлять только PUBLISHED.
При неопределённом commit восстанавливать записанный claim, не пересоздавать работу по таймеру.

Добавить повторяемую очистку staging/исходника после подтверждённого результата.
При окончательной ошибке основного видео очистить его временные объекты и уведомить пользователя.
При ошибке дополнительного шага сохранить видео и успешные дорожки; source=PUBLISHED_MEDIA
не удалять. Очистка должна учитывать актуальную ревизию и не затрагивать чужие файлы.

### B5. Отмена, резерв, дополнительные операции

Отмена пользователем и release для местного видеорезерва — разные действия.
После RUNNING дождаться остановки/истечения права и состояния RELEASED с releaseReceipt;
только тогда создавать устойчивую локальную попытку резерва. Десять минут ожидания —
диагностика задержки, не разрешение на второй запуск. PUBLISHING на резерв не переводить.

Capabilities получать с диспетчера: языки распознавания, направления перевода и доступность
исполнителей. Не считать список языков гарантией любой пары перевода.
При недоступных дополнительных операциях предлагать ручной ввод/дорожки.
Не создавать серверный резерв распознавания/перевода для первой версии.

Аудио возвращает сплошной текст оригинального языка. Видео с выбранными субтитрами — одна
пользовательская задача со steps по языкам. PARTIAL публикует основной результат и успешные
дорожки, сообщает причины остальных. Повтор дополнительных шагов создаёт новую работу
над PUBLISHED_MEDIA; идентичный старый UUID не означает повтор исполнения.

## Фронтенд: после стабилизации DTO бэкенда

Фронтенд обращается к своему бэкенду; токен диспетчера туда не попадает.
Показывать состояния ожидания/обработки/публикации, задержку и понятные причины ошибок.
Не обещать время завершения по одному размеру файла.
Каталог языков и направлений получать через бэкенд, учитывать ONLINE/OFFLINE/NOT_INSTALLED.
При недоступности распознавания/переводов сохранять ручные текст/VTT/SRT.
PARTIAL отображать с готовым видео и перечислением неудачных дополнительных шагов.
Субтитры — отдельные дорожки для плеера; проверить переключение языка на desktop/mobile.

## Приёмка изменений сайта

Тестировать сначала с contract fixtures и HTTP-стендом; затем с реальным диспетчером
и тестовым обработчиком на этапе 4. Проверки схем в worker-server этого не заменяют.

- Обе продуктовые загрузки создают внешнюю заявку с полным профилем, SERVER остаётся рабочим.
- Потеря ответа POST, restart поллера и повторы outbox не создают дубликат обработки/публикации.
- Старый Fence, поздний PUT, смена ревизии и отмена не заменяют актуальное готовое видео.
- Истёкшие GET/PUT обновляются, состав HLS проверяется, повреждённый пакет не становится READY.
- Потеря ответа publication-claim/decision восстанавливается без резервного дубля.
- RELEASED нужен до местного резерва; десятиминутное ожидание не запускает его само.
- PARTIAL сохраняет видео/успешные дорожки, ошибка PUBLISHED_MEDIA не удаляет исходное медиа.
- Окончательная ошибка основной операции очищает только свои временные файлы и уведомляет.

В отчёте агента перечислить изменённые точки, миграции, проведённые проверки и оставшиеся
зависимости от worker-server. Не выдавать работу стенда за готовность VPS.

## Когда выполнять

Диспетчер, WSS-обработчик, FILE-видеопуть и панель уже реализованы локально.
[Текущие границы и необходимые исправления](../audits/readiness-review-2026-10-13.md).
B1–B5 нужно выполнить в репозитории сайта перед совместной приёмкой;
фронтенд — после стабилизации продуктового API бэкенда. Подготовку DTO можно вести
параллельно с исправлением исполнителей worker-server.
