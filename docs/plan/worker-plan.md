# План реализации диспетчера и обработчиков

Дата: 2026-10-13. Этапы 1–7 реализованы: контракт, диспетчер, обработчик, видеопуть,
каталог/аудио/субтитры, панель и поставка/эксплуатация проверены на Windows. Mac проверяется на реальной машине перед приёмкой. Это рабочий план реализации после обсуждения,
а не инструкция запуска готового продукта. Чекбоксы отмечают выполненную работу,
не только согласованное требование. План не запускает развёртывание/изменения сайтов.

не ожидая завершения оформления всей панели.

## Этап 1 — аудит интеграции и контракт

- [x] Получить аудит бэкенда сайта: код, локальные миграции/БД и тесты проверены другим
      агентом, отчёт передан владельцем 2026-10-13. VPS/.env/реальная сеть не проверены.
- [x] Уточнить полный видеопуть курса/урока, не только отдельный handler; существующий
      резерв/политику COPY / ENCODE / SKIP_UPSCALE использовать без повторного изобретения.
- [x] Создать contracts/: версионированные HTTP-схемы, сообщения устройств и общие fixtures.
      Сохранить совместимый базовый operations/jobs или описать явную миграцию клиента.
- [x] Спроектировать состояния задания, шагов, назначения, передачи и публикации;
      ошибка дополнительных операций не удаляет успешное видео/дорожки.
- [x] Спроектировать атомарное назначение одному устройству: ack, срок исполнения,
      продление, отмена, reconnect/reconcile, изолированные поколения выходных объектов.
- [x] Описать каталог возможностей/языков, профиль результата сайта, свежие ссылки,
      динамический перечень HLS, подтверждение публикации, безопасный резерв сайта.
- [x] Выбрать интервалы служебных сообщений, веса очереди, правила повторов и очистки,
      срок ID-дедупликации отдельно от истории. Зафиксировать как технические решения.
- [x] Составить связанные задачи serverBreasts/front: новые DTO/поллер/публикация/уведомления,
      ручной ввод и дорожки. В этом репозитории соседние приложения не переписывать.

Подтверждённые аудитом блокеры интеграции, включить в схемы до реализации клиента:

1. Загрузка урока/канала вызывает локальный async packageVod, не ставит media.transcode.
   Нужен продюсер внешнего задания в продуктовых путях с сохранением локального резерва.
2. Текущий handler читает одно params.quality, по умолчанию P720. Нужен полный
   неизменяемый снимок выбранных качеств и профиля, а не настройки обработчика вместо сайта.
3. HLS сейчас передаётся ZIP с фиксированными outputs. Нужны динамический перечень,
   обновление GET/PUT-ссылок после принятия и проверка пакета перед READY.
4. Ключи outputs зависят от jobId, не поколения попытки. Нужна изоляция attemptId /
   поколения, иначе старый PUT может перезаписать новый результат.
5. complete сейчас доверяет метаданным ответа: добавить проверку реальных объектов,
   размеров/плейлистов и атомарную публикацию в продуктах урока/канала.
6. Нет публичного API отмены и подтверждённого перехода на резерв после принятия;
   нужны контракт, отсечение старой попытки и правильная очистка source/outputs.
7. Нет каталога моделей/направлений и частичного успеха video + subtitles;
   ручные VTT/SRT и текст аудио уже существуют, использовать их.

Клиент operations/jobs и защита от дубля после неопределённого ответа уже есть.
Не писать их заново без необходимости. Сначала общий контракт в worker-server,
затем задачи бэкенда/фронта по этому контракту; не реализовывать расширения по догадкам.

Результат: спецификация v2 и проверяемые примеры готовы; несовместимости outputs/ZIP
описаны в миграции, доработки сайта вынесены в отдельное задание. Это готовность проектирования,
не проверка работающего сервиса. Следующий этап — ядро диспетчера без ожидания замеров Mac.

## Этап 2 — компактный диспетчер

- [x] Go-приложение, миграции SQLite, один активный экземпляр, постоянный том.
- [x] Сайты/операции/приоритеты, отдельные токены сайтов и устройств, выпуск/отзыв,
      изоляция доступа; хешировать проверяемые токены и не выводить их в журнал.
- [x] Атомарный приём и дедупликация «сайт + UUID»: принятие записать до исполнения,
      повтор запроса возвращает существующую работу даже после потери ответа.
- [x] Долговечные очередь/назначения/метаданные, восстановление после restart и crash.
- [x] Справедливый планировщик по сайтам и возможностям устройств: высокий приоритет
      получает больше запусков, остальные продвигаются. Количественные квоты сайтов пока не вводить.
- [x] Записывать историю/ошибки 30 дней по умолчанию с настройкой, сохранять активные
      задачи и компактную дедупликацию отдельно. Не хранить медиа или модели.
- [x] Измерить RAM/CPU/размер контейнера на определённом metadata-стенде;
      целевой бюджет 128–256 МБ не считать доказанным до замера.

Результат: [реализация и замеры](../audits/dispatcher-stage2-2026-10-13.md),
[инструкция запуска](../instruction/dispatcher-development.md). CLI управления — при остановленном
сервисе; admin API/панель позже. На этапе 2 проверено ядро; WSS добавлен на этапе 3.
Замеры 2000 metadata jobs/10 сайтов/20 offline устройств не заменяют будущий замер живых соединений.

Проверка: повтор приёма, restart, два одновременных назначения и два сайта не создают
новой работы с тем же ID, не публикуют чужой результат и не блокируют низкий приоритет.

## Этап 3 — программа обработки и постоянное соединение

- [x] Node.js + TypeScript: общий протокол/состояние, платформенные адаптеры,
      безопасный запуск/остановка дерева процессов, тестовый исполнитель до тяжёлых моделей.
- [x] Исходящий постоянный канал к диспетчеру по токену устройства; сообщения
      характеристик/возможностей/нагрузки, назначения/ack, прогресса и продления.
- [x] На переподключении сверять активные попытки, не перезапускать задачу вслепую.
- [x] Две минуты без связи — настраиваемый срок: истечение прежнего права,
      остановка старого исполнителя, переназначение совместимому устройству.
      Старое сообщение не меняет новое назначение; защита upload/публикации реализуется на этапе 4.
- [x] Отдельно доступность и продвижение: heartbeat не меняет LastProgressAt,
      отсутствие продвижения даёт предупреждение. Сроки тяжёлых операций определить замерами этапов 4–5.
- [x] CPU/RAM/занятость рабочего диска ≥ 80% — новые работы ждут;
      учитывать абсолютный резерв RAM/диска и устойчивое снижение. GPU/VRAM и
      точные оценки памяти/подкачки проверяются при подключении исполнителей на этапах 4–5.
- [x] Автопараллельность с ручным верхним пределом, локальный резерв ресурсов.
- [x] 10 минут ожидания — порог проверки задержки, не дедлайн и не автоматический резерв.

Результат: [отчёт этапа 3](../audits/processor-stage3-2026-10-13.md),
[запуск обработчика](../instruction/processor-development.md).
Windows/Linux, два обработчика, потеря связи/ack, зависание, crash и скачки часов проверены.
Физический сон Mac, реальный внешний SSD и нагрузка тяжёлых исполнителей — приёмка на оборудовании.

## Этап 4 — файлы и полный видеопуть

- [x] Очередь хранит записи, скачать исходник ближе к исполнению; обновлять presigned
      для той же попытки. Не выдавать S3-ключи обработчику и не проксировать медиа диспетчером.
- [x] Настраиваемая рабочая папка и внешний диск, проверка тома/свободного места;
      отключённый диск → ожидание без записи на внутренний SSD.
- [x] files/YYYY-MM-DD/<attempt-id>, модели отдельно. Очистка после успеха,
      при смене даты, старте и ежедневно; сохранять активную работу и незавершённую передачу.
- [x] Перенести правила анализа/видеоупаковки сайта, передавать полный профиль результата;
      фактические качества и пропуск апскейла сохраняются. Запрещена молчаливая подмена профиля.
- [x] Динамический перечень файлов → проверка и ссылки сайта → upload обработчиком
      прямо в хранилище. Объекты разных попыток разделены, число/размер/пути проверяются.
- [x] Сервер сайта проверяет комплектность, публикует и подтверждает; повтор upload/commit
      идемпотентен. Исходник удалять после подтверждения, опубликованный пакет сохранять.
- [x] Существующий резерв видео на сайте включать только по подтверждённому безопасному
      переходу; после неопределённости не запускать дубль. Отсутствие другого устройства
      не равно праву сайта немедленно забрать уже принятую работу.
- [x] Временные сбои передачи повторять до трёх раз с выбранными паузами, готовый
      результат не пересоздавать из-за одного сбоя upload.
- [x] Окончательная ошибка основной операции: код/причина, статус сайта, удаление
      исходника/частичных файлов и уведомление. Отмена отдельно, не затрагивать чужие результаты.

Проверка: полный путь тестового видео, потеря upload/подтверждения, COPY без пересжатия,
низкое разрешение, отказ/отмена, смена даты, отключение SSD; плеер Desktop/Mobile.

Результат: [отчёт этапа 4](../audits/processor-stage4-2026-10-13.md).
Клиент сайта v2 и плеер Desktop/Mobile на рабочем сайте не проверялись: интеграция сайта
ещё в задании. Физический SSD/Mac — приёмка на оборудовании.

## Этап 5 — каталог моделей, аудио и субтитры

- [x] Выбрать и закрепить конкретные исполнители/модели, лицензии, форматы и версии.
      Языки брать из проверенного описания модели, а не фиксировать русский/английский.
- [x] Каталог по ОС/CPU/ускорителю/RAM/VRAM: назначение, языки/направления перевода,

- [x] Команды установки/активации/удаления на выбранном устройстве, скачивание туда,
      прогресс, свободное место и защита активных моделей. Вне каталога — отдельный механизм.
- [x] Аудио → сплошной текст языка оригинала, без перевода/таймкодов/говорящих;
      режимы быстрее/качественнее/автоматически по ресурсам.
- [x] Видео: единая пользовательская задача создания отдельных дорожек для плеера,
      внутренние этапы распознавания/таймкодов/перевода на выбранные доступные языки.
- [x] Сохранять видео/успешные дорожки при ошибке дополнительного шага;
      причины по операциям/языкам возвращать сайту, предусмотреть повтор только нужного шага.
- [x] Без дополнительного резерва на сайте — ручной текст/загрузка субтитров;
      основная обработка видео не блокируется. media.preview остаётся локальной на сайте.

Проверка: разные языки и модели, неподдерживаемое направление, текст аудио,
частичный успех, ручная дорожка и выбор языка плеером. Качество/скорость измеряются
отдельно, замер Windows не обещает производительность Mac.

Результат: [отчёт этапа 5](../audits/processor-stage5-2026-10-13.md).
Реальный whisper.cpp/NLLB, плеер и Mac — приёмка на оборудовании; CI идёт через catalog-test.

## Этап 7 — поставка и эксплуатация

- [x] Dockerfile/Compose, постоянные тома, health/readiness, HTTPS/proxy с WSS,
      перезапуск, ограниченные логи и проверенные лимиты на основном сервере сайта.
- [x] Пакеты обработчиков для Windows/macOS/Linux, закреплённый Node LTS/зависимости,

- [x] Подготовить backup/restore диспетчера: суточный согласованный снимок,

- [x] Restore в отдельной среде, сверка поколений/активных работ, защита от старых результатов;

- [x] Обновление владельцем из панели после текущих работ; dispatcher maintenance,
      сохранение очереди и секретов, snapshot перед миграцией, совместимый откат/restore.
- [x] Дополнить инструкции точными командами поставленных CLI/образов и диагностикой,

Проверка: новый сервер/устройство разворачиваются по инструкции; update/rollback,
reset-password и restore проверены в тестовой среде.

Результат: [отчёт этапа 7](../audits/dispatcher-stage7-2026-10-13.md).
Production VPS и полный путь сайта — этап 8.

## Этап 8 — совместная приёмка и готовность к запуску

- [ ] Проверить production runtime по чеклисту: локальная БД/тесты не доказывают состояние VPS.
- [ ] Проверить аудит и завершить необходимые задачи бэкенда/фронта сайта.
- [ ] Полный путь: сайт → диспетчер → устройство → хранилище → публикация/плеер.
- [ ] Два устройства/несколько сайтов: приоритеты, перегрузка, конкурентное назначение,
      отказ диспетчера, потеря связи/ответа, пауза/сон/перезапуск и отмена.
- [ ] Проверить поздний результат старой попытки, истёкшие ссылки, частичный upload,
      неполный пакет, частичный успех субтитров и безопасный резерв видео.
