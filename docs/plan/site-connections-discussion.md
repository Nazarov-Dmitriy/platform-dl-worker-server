## Точка остановки: начать следующее обсуждение здесь

Владелец попросил проверить уже существующий резерв на сервере сайта. Проверка исходного
кода показала:

- Видео: есть MediaTranscodeJobHandler и общий HlsPackagingService, включая анализ
  исходника и упаковку без лишнего перекодирования. Использовать существующее решение.
- Аудио: есть MediaTranscribeJobHandler, который запускает внешнюю программу модели.
  По умолчанию модель выключена, путь к программе пустой. Для запуска нужны включение,
  существующий исполняемый файл и прохождение проверки памяти TranscriptionCapacity.
  Программа модели в репозиторий не входит.
- Субтитры: LessonSubtitleService принимает и хранит уже готовые дорожки. Автоматическое
  создание и перевод субтитров в просмотренном коде не найдены; их требуется добавить.
- Настройки работающего сервера и установленные на нём программы НЕ проверялись.
  Наличие реализации и фактическая готовность развёрнутого сервера — разные проверки.

**Уточнение владельца 2026-10-13:** основная обработка видео выполняется на сервере
сайта как резерв. Дополнительные операции распознавания и создания/перевода субтитров
на сервере сайта для первой версии не предусматриваем. Если внешний обработчик
недоступен и резервной дополнительной операции нет, сайт показывает понятное сообщение
и предлагает добавить текст расшифровки или загрузить готовые субтитры вручную.
Отсутствие дополнительных возможностей не должно блокировать основную обработку видео
и не должно приводить к удалению успешно обработанного видео.
Предложение обязательного ожидания восстановления вместо ручного ввода не принято.

**Частичный результат согласован:** сохраняем готовое видео и успешные дорожки;
сервис сообщает, какие дополнительные операции/языки выполнить не удалось и почему,
сервер сайта передаёт эту информацию пользователю. Ошибка дополнительной операции
не превращается в ошибку основной обработки и не удаляет успешный результат.

**Диспетчер согласован:** отдельный контейнер на постоянно доступном сервере,
без тяжёлой обработки медиа. Хранит общую очередь, подключения сайтов, токены,
разрешения и приоритеты; определяет доступность устройств и назначает им работу.
Обработчики на Windows/macOS/Linux предоставляют вычислительные ресурсы.

**Следующий вопрос:** конкретные исполнители и состав начального каталога моделей;
периодичность сообщений состояния и детали протокола ещё спроектировать.
Контроль зависания при сохранившейся связи согласован, конкретные сроки — по замерам операций.

Авторизация устройств согласована: диспетчер выдаёт отдельный «Токен устройства»
каждому обработчику. Это тот же принцип секретного токена, что у сайтов, но другие
права: сайт отправляет задания/читает собственные результаты, устройство получает
назначенную работу и сообщает её состояние. Токены не взаимозаменяемы.
В панели создаём устройство, выдаём/отзываем его токен; обработчик настраивается
адресом диспетчера и своим токеном. В интерфейсе использовать названия
«Токен сайта» и «Токен устройства», без отдельного термина «ключ устройства».
Связь согласована: обработчик сам устанавливает постоянное исходящее соединение
с диспетчером, получает назначенные задания и сообщает состояние по этому каналу.
После обрыва автоматически переподключается. Для домашних машин не требуется
публичный адрес или входящие порты роутера. Конкретный протокол и интервалы сообщений
ещё выбрать; отсутствие подтверждённого продления права исполнения учитывает правило двух минут.
Для уже принятого внешнего задания с неопределённым состоянием остаётся необходимым
безопасное разрешение попытки; недоступность связи сама по себе не доказывает её остановку.

## Согласовано: размещение, запуск и панель

- Одна из рабочих машин — Mac владельца. Модель A2686: Mac mini M2 (2023),
  8 ядер CPU / 10 ядер GPU. RAM предварительно 16 ГБ со слов владельца; объём RAM,
  внутреннего диска и реальные характеристики проверяем при первом запуске.
  Для завершения обсуждения включать Mac не требуется.
- Уточнение владельца 2026-10-13: целевые ОС — Windows, macOS и Linux.
  Поддержка не ограничивается Mac; Linux нужен для будущего отдельного компьютера/сервера.
  API, доступ сайтов, очередь и логика панели независимы от ОС. Платформенные функции,
  установка и исполнители обработки отдельные; ускорение, пути и ресурсы настраиваются.
- Программа обработчика согласована на Node.js + TypeScript для Windows/macOS/Linux.
  Управляет файлами, заданиями, ресурсами и связью с диспетчером; тяжёлую обработку
  выполняют запускаемые инструменты FFmpeg и исполнители моделей, выбранные под машину.
  Диспетчер — отдельный компактный сервис на Go; язык обработчика не требует
  совпадения с языком диспетчера, взаимодействие по согласованному протоколу.
- Windows-компьютер для тестов и дополнительной обработки: Ryzen 5 7600X, 6 ядер / 12 потоков,
  64 ГБ DDR5 со слов владельца, RTX 5060 Ti с приблизительно 16 ГБ VRAM по nvidia-smi.
  Владелец хочет подключать Windows к обработке части нагрузки одновременно с Mac.
  Предусмотреть несколько устройств и распределение заданий между ними.
  Тест сайта на Windows → обработчик на Mac в LAN также нужен.
- Каталог моделей должен учитывать ОС, архитектуру CPU, ускоритель, RAM/VRAM и
  совместимый исполнитель/формат модели. Пользователь выбирает подходящий вариант
  перед установкой. Предложено автоматически определять устройство с подтверждением
  в интерфейсе; конкретный экран первого запуска ещё спроектировать.
  Одна модель может иметь варианты для разных исполнителей, не обязательно отдельные
  модели для каждой ОС. Языки и направления берём из проверенного описания конкретной
  версии; если данных нет, оформляем их вручную по документации. Детали каталога ещё выбрать.
- Сервис работает в фоне, управление — через веб-панель в браузере.
- Автозапуск при старте системы включён, его можно отключить в панели.
  Есть отдельная пауза обработки с сохранением доступа к панели.
- Поддерживаются подключения на одной машине через localhost, между машинами в LAN
  и через интернет по HTTPS. Настраиваются адрес прослушивания и порт.
  Публичная точка подключения теперь диспетчер, а не обязательно сам Mac.
  Сетевой канал между диспетчером и обработчиками ещё выбрать.
- Диспетчер публикуется по HTTPS на поддомене существующего домена владельца,
  например jobs.<домен>. Отдельный домен покупать не требуется. Конкретное имя,
  DNS, reverse proxy и автоматическое обновление сертификата выбрать при развёртывании.
  Перенос диспетчера на другой сервер должен сохранять адрес подключения клиентов.
- Панель допускает удалённый доступ по HTTPS. Несколько персональных аккаунтов:
  владелец с полным доступом и управлением пользователями; оператор с доступом к
  очереди, состоянию машины, заданиям и настройкам обработки. Управление доступом
  сайтов — отдельное разрешение. Вход по логину/паролю, журнал действий.
- Восстановление доступа владельца — команда на сервере диспетчера для задания
  нового пароля. Требуется административный доступ к серверу/контейнеру;
  публичного неавторизованного сброса нет, почтовый сервис для восстановления не требуется.
- Из панели можно скачивать, выбирать и удалять модели; проверять свободное место,
  показывать прогресс скачивания. Защиту моделей, используемых активным заданием,
  предусмотреть при реализации.
- Установка моделей из общей панели диспетчера согласована: сначала выбираем устройство,
  затем показываем совместимые с его ОС/архитектурой/ускорителем варианты из подготовленного
  каталога проверенных моделей. Карточка содержит назначение, языки, размер скачивания
  и требования к RAM/VRAM. По команде «Установить» выбранный обработчик скачивает модель
  на свой рабочий диск, а не на сервер диспетчера; состояние/прогресс видны в панели.
  Добавление моделей вне подготовленного каталога предусмотреть отдельно.
- Обновление запускает владелец из панели. Сервис перестаёт запускать новые задания,
  завершает текущие, сохраняет очередь и обновляется. При неудачном запуске новой версии
  требуется откат. Механизм релизов, совместимость данных и миграций ещё спроектировать.

## Согласовано: сайты, возможности и параметры результата

- Сервис владеет ресурсами машины. В панели создают сайты, разрешают операции,
  выдают отдельные токены, задают приоритеты. На сайте вводят адрес сервиса и токен.
- Уточнение архитектуры: адрес сервиса сайта — адрес диспетчера. Настройки сайтов,
  их токены, разрешения, приоритеты и общее состояние заданий хранятся централизованно
  у диспетчера; общая административная панель относится к нему.
  Настройки отдельных устройств (рабочий диск, модели, пределы ресурсов, автозапуск)
  исполняются на соответствующем обработчике. Канал управления этими настройками,
  хранение желаемой конфигурации и локальный доступ ещё спроектировать.
- Сайт обращается к сервису, старая pull-схема claim/heartbeat отменена.
  Отдельный токен сайта доказывает доступ; адрес сайта сам по себе не является авторизацией.
- Фронтенд получает возможности через сервер своего сайта; сервер запрашивает сервис
  с токеном. Токен не передаётся в браузер.
- Сервис — источник актуальных операций, языков распознавания, направлений перевода,
  доступных форматов результата. Смена модели не требует вручную менять все сайты.
  Одного списка «восемь языков» недостаточно: направления перевода могут отличаться
  от языков распознавания и зависеть от исходного языка.
- При недоступности сервиса показывать понятный статус. Предложены последний известный
  каталог и ручное указание языка; точное поведение при отсутствии каталога ещё уточнить.
  Ранее полученный каталог не гарантирует допуск: проверка при каждом приёме задания.
- Сайт задаёт требуемый результат: разрешение, профиль качества/сжатия, формат,
  субтитры и языки. Сервис выбирает совместимые инструменты и ускорение.
  Нельзя молча заменить запрошенный профиль более низким ради ресурсов.
- Поддерживаем существующую политику видео сайта, в том числе пропуск апскейла:
  не создавать 1080p из 720p. Это уже существующее правило, а не произвольное снижение
  качества исполнителем. Сайт должен получать фактический состав результата.
- Если нужная возможность не поддерживается или не разрешена, возвращаем понятную причину.

## Согласовано: аудио, видео и субтитры

- Аудио: распознавание речи, только сплошной текст на языке записи, без перевода,
  таймкодов и разделения по говорящим. Модель устанавливается и выбирается на сервисе.
- Режимы распознавания: быстрее, качественнее, автоматический выбор из установленных
  совместимых моделей по ресурсам и настройкам владельца.
- Видео: одно пользовательское задание на создание субтитров. Распознавание,
  таймкоды и перевод на выбранные языки — внутренние шаги сервиса.
  Не считать перевод отложенным по умолчанию: владелец вернул его в обсуждаемую задачу.
- Субтитры — отдельные дорожки для загрузки в плеер и выбора языка, без вшивания
  в изображение. SRT / VTT предложены; точный набор форматов и контракт ещё выбрать.
- Частичный результат: готовое видео и успешные дорожки сохраняются и доступны;
  сервис возвращает перечень неудавшихся дополнительных операций/языков с причинами,
  сервер сайта показывает их пользователю. Ручная загрузка недостающих дорожек доступна.
  Повтор только неудавшейся операции предложен, точный механизм ещё спроектировать.
- Модель распознавания может быть общей для аудио и видео; перевод отдельным инструментом
  по необходимости. Конкретные инструменты, модели и направления ещё не выбраны.
- Видеоупаковка использует уже решённую задачу «Видео: упаковка без лишнего перекодирования»,
  закрытую 2026-10-01. FFprobe + политика COPY / ENCODE / SKIP_UPSCALE,
  проверка совместимости, частоты/ключевых кадров и битрейта, потолок при кодировании.
  Перенос на другой исполнитель обязан сохранять параметры и правила сайта.
  Низкий битрейт сам по себе не гарантирует COPY: есть другие проверки совместимости.
- Начальные операции клиента: media.transcribe и media.transcode; media.preview локальная.
  Код операции для комплексного создания субтитров и взаимодействие с транскодированием
  определить как расширение существующего контракта.

## Согласовано: очередь, ресурсы и резерв

- Для нескольких устройств требуется общая координация очереди: при назначении задания
  оно атомарно закрепляется за одним исполнителем и отмечается как взятое в работу.
  Второе устройство получает следующее подходящее задание, не ту же работу.
  Одной независимой проверки статуса недостаточно из-за одновременного доступа.
  Закреплять до скачивания/запуска модели; выбор следующего учитывает приоритеты,
  возможности и ресурсы устройства. Место диспетчера и протокол назначения ещё выбрать.
  Это расширение архитектуры; не предполагать, что текущий клиент с одним serviceUrl
  уже умеет распределять нагрузку. Не возвращать отменённый pull-контракт автоматически.
- Общий диспетчер разворачивается отдельным небольшим контейнером на сервере.
  Выполняет координацию/приём/учёт, не запускает модели и перекодирование.
  Обработчики могут подключаться и отключаться независимо; ресурсы предоставляют
  обычные Windows/macOS/Linux-машины. Их доступность и возможности учитывает диспетчер.
  Долговечные данные очереди/конфигурации должны переживать замену контейнера.
  Медиа скачиваются/загружаются обработчиками напрямую через хранилище сайта.
- Для компактного диспетчера предложены Go + SQLite и статическая веб-панель;
  владелец согласился с вариантом малого контейнера на основном сервере сайта.
  Планируемый сервер со слов владельца: около 4 ядер и минимум 8 ГБ RAM.
  Начальный целевой бюджет контейнера 128–256 МБ RAM, ориентир лимита 256 МБ,
  образ — десятки МБ. Это проектные оценки, не измеренные требования/гарантии;
  проверить после реализации. Отдельный VPS диспетчеру не обязателен.
  Окончательное оформление выбора базы/технологий и объём истории ещё определить.
- На сайте сохраняется собственная задача; сервис хранит принятую очередь долговечно,
  восстанавливает состояние после перезапуска. Способ восстановления незавершённой работы
  и необходимость повторной обработки уточнить.
- Очередь — записи без предварительного скачивания всех файлов. Исходник скачивается
  ближе к исполнению; нужны свежие временные ссылки, если старые истекли.
- Пока НЕ вводим количественные лимиты очереди для каждого сайта, а собираем статистику:
  длина очереди, ожидание, скорость и нагрузка. Ограничения машины и проверки файлов остаются.
- Приоритет настраивается отдельно для сайта. Высокий приоритет получает больше запусков,
  остальные очереди постепенно двигаются. Без строгого вытеснения остальных и без прерывания
  текущего задания ради нового приоритетного. Конкретные веса/алгоритм выбрать.
- Автоматическая параллельность: при свободных ресурсах запускать дополнительное задание,
  с ручным верхним пределом. Скачивание/загрузку по возможности совмещать с обработкой.
  Начальную параллельность и оценки памяти исполнителей проверяем замерами.
- Начальные настраиваемые пороги: CPU ≥ 80%, RAM ≥ 80% или рабочий диск заполнен ≥ 80%
  → новые задания не запускаются / новые файлы не скачиваются. Уже запущенные продолжаются.
  Дополнительно учитывать ожидаемые потребности задания, абсолютный запас диска,
  нагрузку аппаратного кодировщика и устойчивое снижение нагрузки перед новым запуском.
  На Mac учитывать давление памяти/подкачку, а не только грубый процент RAM.
- 10 минут — НАСТРАИВАЕМЫЙ ПОРОГ ЗАДЕРЖКИ очереди, не дедлайн обработки и не автоматический
  переход на резерв. Если сервис отвечает и задания продвигаются, продолжаем ждать Mac.
  Размер в ГБ не определяет время: важны длительность, параметры, число дорожек и передача.
  Быстродействие Mac относительно сервера не измерено и не гарантируется для всех операций.
- Резерв на сервере сайта при определённом отказе / недоступности до передачи уже предусмотрен,
  если включён и поддерживает операцию. Потерянный ответ после отправки не равен отказу.
- Уточнение 2026-10-13: резерв сайта выполняет основную обработку видео.
  Дополнительные операции распознавания/генерации/перевода субтитров на сервере сайта
  в первой версии не планируем. При их недоступности показываем причину и предлагаем
  ручной текст расшифровки или загрузку готовых дорожек; основное видео сохраняем.
- После принятия/неопределённого ответа нельзя просто запустить дубль на сайте.
  Уточнение 2026-10-13: после двух минут без связи с назначенным устройством диспетчер
  переназначает задание другому доступному совместимому исполнителю. Если связь
  восстановилась раньше, работа остаётся у прежнего. Срок настраиваемый и не является
  ограничением длительности обработки или ожидания в очереди.
  Если другого устройства нет, основная обработка видео может перейти на резерв сайта;
  для дополнительных операций без резерва действует ручной ввод/загрузка результата.
- Право исполнения ограничено сроком и продлевается при связи с диспетчером.
  По истечении права старый исполнитель обязан остановить работу, а его поздний
  результат не принимается. Конкретные протокол продления, часы, идентификаторы попыток,
  изоляция объектов результатов и проверка перед публикацией ещё спроектировать.
  Не допускать перезапись новой попытки старыми presigned-ссылками.
  Для сайта неопределённый ответ по-прежнему не разрешает самовольный дубль:
  решение о переназначении централизовано у диспетчера. Старый claim/heartbeat сайта отменён.
- Устройство отдельно сообщает доступность и состояние работы: этап и признаки продвижения.
  Если связь есть, но продвижения долго нет, помечаем задание как подозрительное
  и проверяем перед остановкой/переназначением. Сроки настраиваются по операциям
  и выбираются по замерам; длительная обработка сама по себе не считается зависанием.
  Не требовать непрерывного роста числового progress от инструментов, которые его не дают;
  конкретные признаки активности и способ проверки ещё определить.
- Отключение сайта запрещает новые задания, уже принятые завершаем. Отдельное действие
  отменяет одно или все задания сайта, включая выполняемые, с очисткой и статусом «Отменено».
  Отзыв токена и доступ к окончательному статусу требуют отдельного решения.

## Согласовано: результаты, хранение, ошибки и очистка

- Файлы передаются через временные presigned-ссылки. Сервис не получает ключи S3
  и доступ к БД сайта.
- Mac готовит HLS-пакет (качества, сегменты, плейлисты) и дорожки субтитров, передаёт
  серверу сайта перечень файлов, получает временные ссылки и загружает прямо в хранилище.
  Сервер сайта проверяет комплектность и только затем публикует результат.
  Не пересылать весь медиапакет через сервер сайта ради последующей загрузки.
- Существующий контракт имеет фиксированные outputs, а текущий серверный исполнитель
  media.transcode загружает ZIP. Динамическая выдача ссылок на сегменты и приём их перечня
  — согласованное направление доработки, а НЕ уже реализованное поведение.
- Если передача прервалась, повторяем загрузку готовых файлов, сохраняя их на Mac до
  подтверждения. Не перекодировать всё заново только из-за сбоя загрузки.
- После успешной проверки и завершения задания сервер сайта удаляет исходник из хранилища,
  сервис очищает рабочие файлы. При COPY не удалять объект, ставший готовым результатом:
  исходник и опубликованный результат должны иметь однозначный жизненный цикл.
- Временные сбои скачивания/загрузки: до трёх повторов с паузами.
  Уточнить, означает ли это три повтора сверх первой попытки, и выбрать интервалы.
  Пока повторы продолжаются, сохраняем необходимые файлы.
- Окончательная ошибка: сервис отдаёт стабильный код и понятную причину; сервер сайта
  обновляет статус задания/видео, удаляет исходник и частичные результаты, уведомляет
  пользователя о неудаче и необходимости повторной загрузки. Сервис очищает рабочие файлы.
  Запись ошибки сохраняется для диагностики. Это заменяет прежнее предложение хранить
  исходник после окончательной ошибки. Не удалять уже опубликованные независимые результаты.
- Это правило удаления относится к окончательной ошибке основной обработки.
  При частичном успехе видео/успешные дорожки сохраняются, ошибки дополнительных
  операций возвращаются пользователю отдельно. Не применять очистку всего видео
  из-за ошибки распознавания, перевода или отдельной дорожки.
- Отмена — отдельный статус, очищаем относящиеся к заданию файлы и обновляем состояние сайта.
  Уточнить состав уведомления при отмене; при частичном успехе передаём пользователю
  перечень невыполненных дополнительных операций и причины.
- Рабочая структура сервиса: files/YYYY-MM-DD/<ID-задания>/.
  Новую дату создаём при необходимости; завершённые папки удаляем сразу.
  При новой дате, запуске сервиса и раз в сутки проверяем все старые папки, удаляем
  ненужные файлы и пустые даты. Активную работу, в том числе начатую до полуночи,
  и незавершённую передачу не удалять. Остатки после падения сверять с долговечным состоянием.
  Срок очистки осиротевших и зависших файлов ещё определить.
- Рабочая папка выбирается в настройках. Позже владелец планирует SSD в док-станции
  для Mac mini; исходники, результаты, модели и временные файлы направлять сразу туда,
  без промежуточной записи больших файлов на внутренний SSD.
  Смена папки без переустановки; процедуру переноса при активных задачах ещё определить.
- Если выбранный диск отключён/заполнен, приостанавливать новые задания, без автоматического
  переключения на внутренний диск. Системная подкачка macOS остаётся на загрузочном диске;
  внешний SSD не увеличивает RAM и не исключает все записи системы на внутренний диск.
- Токены, presigned-ссылки и содержимое расшифровки не должны утекать в журналы
  или ответы других сайтов. Сайт видит только свои задания/результаты.
- История заданий и ошибок в панели хранится 30 дней по умолчанию, срок настраивается.
  Сохраняются сайт, устройство, время обработки, результат и причина ошибки;
  это метаданные, а не медиофайлы или полный текст расшифровки.
  Удаление истории не должно стирать активные задания или разрешать повторное исполнение
  старого ID: срок/форма хранения записей дедупликации определяются отдельно.
  Срок журнала действий пользователей ещё определить.
- Резервное копирование диспетчера: раз в сутки, последние семь копий как начальный
  ориентир, без медиа и моделей. Уточнение владельца: сохранять копию на самом сервере
  и во внешнем хранилище, используя существующий механизм проекта сайта.
  В serverBreasts есть deploy/scripts/backup-postgres.sh: сжатый дамп в deploy/dump,
  проверка архива/контрольная сумма, локальная ротация и off-site загрузка в S3.
  По умолчанию существующая локальная ротация — 14 дней; это не менять для сайта
  только из-за новых настроек диспетчера. Загрузка в S3 зависит от настройки.
  Для диспетчера выделить отдельный бакет или префикс; точный вариант ещё выбрать.
  Существующий PostgreSQL-дамп не копирует будущую SQLite-базу: адаптировать создание
  согласованного снимка под выбранную базу, переиспользовать передачу/проверку/ротацию.
  Настроить очистку обеих копий и проверить восстановление. После восстановления
  сверять активные попытки с устройствами/сайтами, не повторять работу вслепую.

## Текущий контракт клиента: не смешивать с будущими расширениями

Источник: ../../../serverBreasts/docs/instruction/worker-jobs-api.md.

- Bearer-токен на запросах. GET /api/site/operations возвращает operations: массив кодов.
  Расширенный каталог языков/направлений/форматов ещё проектируется.
- POST /api/site/jobs: id UUID попытки, type, params, source (url/objectName),
  outputs (name/objectName/uploadUrl), maxOutputBytes. Приём одним запросом, без отдельного ping.
- 200/202: id и ACCEPTED / QUEUED / RUNNING / SUCCEEDED / FAILED / REJECTED.
  REJECTED содержит стабильный code. Коды отказов не означают, что согласованы квоты сайта.
- GET /api/site/jobs/{id}: тот же id, status, progress 0…1;
  SUCCEEDED: results (name/objectName/bytes/contentType); FAILED: code, permanent.
- Дедупликация по паре «сайт + ID», запись принятия до исполнения. Повтор возвращает
  существующее задание; обновлять можно ссылки на те же объекты, а не операцию/назначение.
- 401/403/429 первой отправки — отказ до приёма. После неопределённости такие ответы
  не разрешают дубль. Тайм-аут / 5xx могут означать потерянный ответ.
- Сайт сохраняет снимок подключения принятой попытки: изменение адреса/токена не теряет
  проверку старой работы. Отзыв токена не доказывает остановку задания.
- Отмена, безопасное переключение, расширенный каталог и динамические HLS-файлы требуют
  согласования версии контракта и изменения клиента сайта, а не только реализации сервиса.

## Оставшиеся вопросы на 2026-10-13

1. Общая очередь/конфигурация сайтов размещены в отдельном контейнерном диспетчере.
   Начать с подключения/авторизации устройств, сетевого назначения, состояния работы
   и деталями безопасного повторного назначения: согласовано две минуты без связи,
   истечение права старого исполнителя и отказ от его позднего результата.
   Затем выбрать инструменты/модели для Windows/macOS/Linux. Частичный успех
   согласован: сохраняем готовые результаты, причины дополнительных ошибок показываем
   пользователю. Резерв видео существует; дополнительные операции без резерва
   заменяются ручным вводом/загрузкой результата.
2. Выбрать инструмент распознавания и перевода, набор моделей/языков, автоматическое
   определение исходного языка, форматы дорожек и поведение при смешанной речи.
3. Уточнить единое видеозадание: упаковка + субтитры или отдельные связанные задания;
   технические статусы частичного результата и повтор неудавшейся операции.
4. Версионировать расширения API: каталог возможностей, параметры профиля сайта,
   динамический перечень файлов/выдача ссылок, подтверждение публикации, отмена,
   прогресс и время последнего продвижения, восстановление после перезапуска.
5. Безопасно переключать уже принятую работу при сбое/зависании и определять зависание
   отдельно от нормального ожидания очереди и длительной обработки.
6. HTTPS-поддомен диспетчера и постоянное исходящее соединение обработчика согласованы,
   без входящих портов домашнего роутера. Выбрать протокол, интервалы сообщений,
   подтверждение назначения/продления и восстановление канала после обрыва.
   Отдельные токены устройств согласованы; уточнить разделение API/панели, ротацию токенов
   и статус после отзыва доступа; не использовать один секрет для людей, сайтов и устройств.
7. Выбрать долговечное хранилище очереди и срок ID дедупликации.
   История заданий/ошибок — 30 дней по умолчанию, настраивается; отдельно определить
   журнал действий, сроки дедупликации и детали восстановления резервной копии.
   Копирование раз в сутки локально + внешнее хранилище согласовано; использовать
   существующий механизм с адаптацией к базе диспетчера. Восстановление владельца согласовано:
   команда сброса пароля на сервере диспетчера.
8. Уточнить веса справедливой очереди, повторные попытки/паузы, очистку осиротевших
   заданий и перенос рабочей папки на внешний диск.
9. Спроектировать установку, релизы, обновление и откат с совместимостью базы;
   определить порядок реализации и проверки Windows/macOS/Linux. Все три ОС целевые.
   Разделение технологий согласовано: Go для диспетчера, Node.js + TypeScript
   для платформенных обработчиков; конкретные исполнители моделей ещё выбрать.
10. При первом запуске проверить Mac, RAM/диск и выполнить замеры одного/нескольких заданий;
    по ним выбрать модели, параллельность и оценки потребления ресурсов.
