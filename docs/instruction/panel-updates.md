# Обновления Worker через панель

Версии: `worker-vMAJOR.MINOR.PATCH`, например `worker-v0.1.0`. Обычный push не обновляет VPS.
Тег запускает `.github/workflows/release.yml`: тесты, готовый Linux amd64 образ внутри пакета,
проверка установки/TLS/WSS/переезда, публикация GitHub Release с `worker-update.json` и SHA-256 пакета.
Теги выпущенных версий повторно не использовать. Реестр Docker и сборка на VPS не нужны.

На VPS `worker install` автоматически устанавливает root-службу
`worker-updater-worker-dispatcher.service` (Linux с systemd). Панель получает только Unix-сокет
службы через read-only bind mount `/updater`; Docker socket и GitHub credential ей не передаются.
Проверить/установить обновление может только OWNER, изменение требует CSRF.

В панели: **Обновления → Проверить обновления → Установить обновление**.
Служба принимает только номер версии и получает пакет из фиксированного репозитория
`Nazarov-Dmitriy/platform-dl-worker-server`. Скачивание идёт с GitHub по HTTPS;
проверяются манифест, SHA-256, состав архива, версия образа и fingerprint загруженного образа.
Downgrade и параллельная операция запрещены. Автоматического обновления без нажатия нет.

После загрузки включается обслуживание. Активные назначения завершаются, новые остаются
в очереди. Ожидание ограничено 30 минутами. Затем контейнер останавливается, полная копия
данных и прежний `.env` сохраняются в `instance/updates-backups/` (доступ root).
Новый контейнер должен пройти Docker healthcheck и проверку HTTPS с прежним CA.
При ошибке восстанавливаются прежние данные, образ и версия. Журнал восстановления
`instance/updater-journal.json` позволяет вернуть прежнюю версию после перезапуска updater.
Если обслуживание было включено владельцем заранее, обновление сохраняет его включённым.
После обновления страница перезагружает интерфейс из нового контейнера.

Существующему экземпляру один раз нужен установочный переход на пакет со службой обновления
и новым API. Последующие совместимые версии устанавливаются из панели. Протокол обновления 1
обновляет образ, VERSION и release.env; изменение самого host-updater или схемы compose потребует
отдельного совместимого установочного перехода, а не исполнения скриптов из скачанного пакета.

Конфигурация:

| Параметр | Источник / default | Назначение |
|---|---|---|
| `DISPATCHER_UPDATER_SOCKET` | compose: `/updater/update.sock`; вне пакета пусто | Unix-сокет; пустое значение отключает обновления в API |
| `WORKER_RELEASE_VERSION` | CI: тег; локально `worker-v0.0.0` | Версия готового пакета; только стабильный SemVer |
| `WORKER_UPDATER_SERVICE` | установщик: `1`; smoke: `0` | Автоустановка systemd-службы; отключение используется на изолированных тестовых стендах |
| `GH_TOKEN` | environment root-службы; пусто | Не нужен для публичного репозитория; при закрытии репозитория потребуется Contents:read, не передавать контейнеру |

Логи: `journalctl -u worker-updater-worker-dispatcher.service`. Резервные копии не удаляются
автоматически в первой версии; нужно учитывать свободное место перед следующими обновлениями.

## Проверки

- Python: `python3 -B -m unittest discover -s deploy/package/tests -v` (Linux).
- Go: `go test ./...`; Linux vet/race выполняются сборкой Docker test target.
- Изолированный пакет: `sudo python3 -B deploy/package/tests/smoke.py ПАКЕТ.tgz`.
- Browser: отдельный вход/панель, обе темы + системная, сохранение темы, мобильная навигация,
  OWNER/OPERATOR, проверка версии, блокировка кнопок во время операции, повторное подключение.

Документация API поставщиков: [GitHub Releases](https://docs.github.com/en/rest/releases/releases),
[Docker Compose up](https://docs.docker.com/reference/cli/docker/compose/up/).
