# Архитектура и границы реализации

Дата: 2026-10-13. Архитектура всей системы; ядро Go/SQLite реализовано на этапе 2.
Текущие возможности и команды: [dispatcher-development.md](dispatcher-development.md).
[Решения владельца](../plan/site-connections-discussion.md) имеют приоритет.
[План](../plan/worker-plan.md), [аудит бэкенда сайта](./site-backend-readiness.md).

## Три участника

| Участник | Ответственность | Постоянные данные |
| --- | --- | --- |
| Бэкенд сайта | Пользовательская задача, профиль результата, ссылки хранилища, проверка и публикация, резерв видео, уведомления | Видео/дорожки и их привязки, задача сайта, снимок внешней попытки |
| Диспетчер Go | Приём, очередь, приоритеты, назначение, токены сайтов/устройств, аккаунты и панель | SQLite как начальный вариант, настройки, попытки, дедупликация, история |
| Обработчик Node.js/TypeScript | Ресурсы, скачивание, FFmpeg/модели, прямой upload, очистка, состояние | Модели, локальное состояние активных попыток, рабочие файлы |

Сайты отправляют запросы диспетчеру. Обработчики подключаются исходящим постоянным
соединением; публичный адрес домашней машины не нужен. Тяжёлые данные идут между
хранилищем сайта и обработчиком. Настройки моделей/диска исполняются на выбранном устройстве.

## Предлагаемая структура репозитория

Структура для реализации, каталогов с кодом ещё нет:

```text
dispatcher/          Go API, scheduler, auth, storage, embedded static UI
processor/           Node.js/TypeScript, protocol, platform adapters, executors
panel/               исходники общей панели, статическая production-сборка
contracts/           схемы HTTP/сообщений, версии и примеры, общие fixtures
deploy/              Dockerfile/Compose, proxy example, backup/restore для диспетчера
docs/instruction/    инструкции развёртывания, аудита сайта и обработки сбоев
```

## Проектные решения, которые проверяем при реализации

- Один активный диспетчер + SQLite на локальном постоянном томе для старта.
  Несколько устройств не требуют нескольких экземпляров диспетчера. Для реплик
  диспетчера нужна отдельная координация/БД, не запускать две SQLite-копии независимо.
- Предлагаемый канал устройств — WebSocket поверх HTTPS (WSS), с прикладными
  подтверждениями, версиями сообщений и обновлением прав исполнения.
  Контракт и интервалы определены в [contracts/v2](../../contracts/README.md).
- Сайт → диспетчер: сохранить текущий контракт приёма/опроса там, где совместим;
  расширения языка/субтитров/HLS/частичного результата версионировать.
- Идентификаторы: сайт + UUID задачи/попытки сайта; отдельный ID назначения устройства
  и поколение исполнения. UUID повторного HTTP не создаёт новую задачу.
- Назначение атомарно меняет состояние и записывает устройство/срок права в транзакции.
  Подтверждение получения и сверка после переподключения исключают повторный запуск.
- Две минуты без подтверждённой связи — переназначение с истечением прежнего права.
  Исполнитель проверяет право и останавливает процесс при его истечении.
  Диспетчер отвергает поздние сообщения, выходные объекты попыток изолированы,
  сайт публикует только результат действующего поколения.
- Нельзя обещать физическое отсутствие краткого перекрытия вычислений при зависании
  ОС/процесса. Гарантируем единственное действующее право и публикацию только его
  результата; способы остановки и временные границы проверяем отдельными fault-тестами.
- Если диспетчер недоступен, обработчик не продлевает право локально и не начинает
  новую работу. Восстановление из старой копии требует смены поколения/сверки попыток,
  иначе есть риск принять результат уже заменённой работы.
- Справедливые веса по сайтам, без начальных количественных квот; ресурсы устройств
  и глобальный резерв ограничивают запуск. Возможности устройств учитываются перед назначением.
- Состояния выполнения, передачи и публикации раздельные: обработано ещё не значит
  опубликовано. Для видео/дорожек нужны независимые результаты шагов и причины ошибок.
- Временные ссылки обновляет сайт для той же попытки; перечень динамических результатов
  проверяется до выдачи PUT. Завершение upload и подтверждение публикации идемпотентны.
- Токены сайта и устройства имеют разные области доступа. Админский аккаунт не
  заменяет технический токен; секреты не попадают в сообщения панели/логи.
- История 30 дней отдельно от минимальных записей дедупликации. В первой версии хранить
  компактные записи завершённых ID без автоматического срока удаления, не переисполнять
  забытый старый ID после удаления истории.

## Контрактные документы этапа 1

HTTP-схемы сайта/панели и схемы сообщений устройств подготовлены в
[contracts](../../contracts/README.md); [задание интеграции](../plan/site-integration-stage1.md).
При реализации соблюдать следующие требования:

1. Обратная совместимость или явная миграция operations/jobs текущего клиента.
2. Регистрация возможностей, назначение/ack, статус/продление, отмена, reconnect/reconcile.
3. Каталог моделей с происхождением/версией, лицензией, требованиями и проверкой загрузки.
4. Языки распознавания и направления перевода, наличие установленного исполнителя.
5. Профиль видео сайта, обновление ссылок, перечень объектов, upload и публикация.
6. Частичные результаты, стабильные ошибки, повтор отдельных шагов и резерв сайта.
7. Версии клиентов, признаки неподдерживаемой версии и безопасный отказ.

Точные URL новых API и поля сообщений утверждаются в контракте. Не выдавать имена
из этого описания за уже существующие маршруты. Изменения бэкенда/фронта сайта
выполняются в их репозиториях после аудита по отдельному плану.
