# Сервер диспетчера: подготовка и будущий запуск

Дата: 2026-10-13. Это чеклист подготовки и требования к будущей поставке.
Образ/Compose/CLI ядра уже реализованы на этапе 2; локальные команды и границы:
[dispatcher-development.md](dispatcher-development.md). Production-поставка, HTTPS,
backup/restore и полный медиапуть ещё впереди. Не разворачивать исторический config.example.json.

## Что нужно на сервере

- Linux-сервер с административным доступом; допускается основной сервер сайта.
  Ориентир владельца — около 4 CPU и минимум 8 ГБ RAM на весь сервер.
- Docker Engine и Compose либо совместимый принятый механизм контейнерного запуска.
- HTTPS-поддомен существующего домена и DNS на сервер диспетчера.
- Reverse proxy с сертификатом и автоматическим продлением; можно использовать уже
  установленный proxy сайта, не занимать его порты вторым независимым сервером.
- Постоянная локальная папка/том для БД и настроек вне заменяемого контейнера,
  каталог локальных бэкапов, внешнее S3-хранилище для второй копии.
- Исходящий доступ к хранилищу резервных копий и службам сертификатов; HTTPS-вход
  для сайтов/обработчиков. Порт БД SQLite наружу не нужен.

Диспетчер не требует FFmpeg, GPU или моделей. Основной сервер сайта может отдельно
требовать FFmpeg/FFprobe для собственного резерва — это проверяет
[аудит бэкенда](./site-backend-readiness.md).

## Ресурсы и постоянные данные

- Целевой бюджет контейнера — 128–256 МБ RAM. Стартовый предел 256 МБ проверить
  нагрузочным тестом с UI/устройствами/БД; не считать гарантией до измерений.
- CPU-лимит выбрать по измерениям без ухудшения продления права исполнения.
  Проверить запас всего хоста, где также работает сайт.
- На диске нужны образ/предыдущий релиз, SQLite и его служебные файлы,
  ротация журналов, локальные копии. Медиа и модели не хранятся на диспетчере.
- SQLite размещается на локальном файловом томе с корректными блокировками;
  в первой версии один активный экземпляр, не shared SQLite на произвольном сетевом диске.
- Логи контейнера ограничить по размеру/числу файлов. Docker позволяет настроить
  max-size/max-file для json-file: [официальная документация](https://docs.docker.com/engine/logging/drivers/json-file/).

## Чеклист развёртывания после реализации

1. Выбрать закреплённую версию образа и проверить поддерживаемую архитектуру сервера.
2. Создать постоянные тома и отдельные права доступа; сохранить bootstrap/recovery
   материалы и серверные секреты вне публичных файлов.
3. Настроить домен/TLS/proxy. Для WSS-канала проверить upgrade и idle timeout;
   [требования nginx](https://nginx.org/en/docs/http/websocket.html).
4. Запустить контейнер с политикой перезапуска, лимитами и ограниченными логами;
   проверить миграции, доступность БД, health/readiness и отсутствие медиапроцессов.
5. Создать первого владельца через будущий bootstrap-механизм, сменить временный
   пароль. Проверить роли оператора и административную команду сброса пароля.
6. Создать сайт/токен сайта и устройства/их токены. Проверить отказ для чужого типа
   токена, отзыва и повторного подключения. Токены не публиковать в отчёте.
7. Подключить первое устройство, выполнить тестовое задание; затем второе и проверить
   однократное назначение, нагрузку, потерю связи и восстановление состояния.
8. Подключить бэкенд сайта после [его аудита](./site-backend-readiness.md), проверить
   полный путь на тестовом видео и ручной ввод при отсутствии дополнительной операции.
9. Настроить суточный backup локально + S3, ориентир семь копий; проверить restore
   в отдельной среде. Проверить очистку истории 30 дней без утраты дедупликации.
10. Записать версии, пути, параметры лимитов, как проверить состояние и как восстановиться.

## Резервное копирование, обновление и восстановление

Использовать существующий механизм backup сайта, но отдельный бакет/префикс и snapshot
базы диспетчера. Для SQLite с работающими записями нужен согласованный снимок через
backup API / подходящую команду, не копирование одного live-файла вслепую.
[SQLite Online Backup](https://www.sqlite.org/backup.html).
В копию включить данные и материалы, необходимые для восстановления доступа/секретов,
с ограничением доступа; медиа и модели исключить.

Обновление диспетчера и обработчика — разные процедуры. Для обновления диспетчера
нужен режим обслуживания: не назначать новые задачи, дождаться согласованной остановки/
завершения текущих и не вызвать ложное переназначение при рестарте. Создать проверенный
snapshot до миграции, сохранить предыдущий образ. Откат образа допустим только при
совместимой схеме; иначе восстановление данных по предусмотренной процедуре.

После restore не выдавать задания из старого snapshot как новые без сверки с сайтами/
устройствами. Предусмотреть смену поколения восстановления и отсечение старых результатов.
Отдельно проверить последствия потери последних суток изменений: суточный backup
не обещает восстановление всех заданий, принятых после него.

## Что появится вместе с кодом

Dockerfile/Compose, пример конфигурации без секретов, proxy-пример, health/readiness,
bootstrap/reset-password CLI, backup/restore, upgrade/rollback и диагностическая команда.
До появления этих артефактов сервер можно подготовить, но приложение запустить нельзя.
