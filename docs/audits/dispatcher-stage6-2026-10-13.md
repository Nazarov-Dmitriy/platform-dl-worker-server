# Этап 6: общая панель и admin API

Дата: 2026-10-13. Реализованы аккаунты, сессии, статическая панель и живое
управление очередью/устройствами/моделями. Соседние сайты и VPS не менялись.

## Реализация

Пароли — argon2id, не SHA256. Сессия — cookie `dispatcher_session` (HttpOnly,
SameSite=Strict, Secure при TLS), CSRF в JSON сессии и заголовке `X-CSRF-Token`.
Лимит входа: 5 неудач / 15 минут на логин+IP → 429. Журнал audit тот же, что у
очереди (30 дней, `-audit-days`).

Роли: OWNER — аккаунты, токены устройств, журнал; OPERATOR — очередь, устройства,
модели; сайты и токены сайтов — только OWNER или `manageSites`. Оператор не видит
секреты и метаданные токенов устройств. Неподключённое устройство в списке
`online: false`. Токен plaintext один раз; повтор того же requestId — 409
TOKEN_SECRET_ALREADY_ISSUED.

Панель: `GET /panel/` (корень редиректит). CLI при остановленном диспетчере:
`owner-bootstrap -login -password`, `owner-reset-password` (инвалидирует сессии,
почты нет). Команда CONFIGURE пишет желаемые настройки; подтверждённые видны
после SUCCEEDED на устройстве. Автозапуск — флаг в журнале обработчика; установка
OS-сервиса — этап 7. Обновление диспетчера из панели — этап 7.

## Проверки

Windows: `go test ./...` (в т.ч. оператор без device token/accounts, CSRF, rate
limit, одноразовый site token, сброс пароля владельца); 20 Node tests без регрессии.

Не проверено: HTTPS/cookie Secure за прокси, реальный автозапуск Windows/Mac,
роль оператора в браузере у владельца.
