# Этап 2: ядро диспетчера и локальная проверка

Дата: 2026-10-13. Реализовано в worker-server; serverBreasts/front, production VPS,
.env, рабочие задания и пользовательские файлы не изменялись.

## Реализация

Go 1.27.0, SQLite без CGO, миграция 001, WAL/synchronous FULL, OS-блокировка одного
активного экземпляра на БД. HTTP v2 приём/опрос/capabilities/cancel/release и server CLI.
Отдельные SITE/DEVICE токены, 256 случайных бит, хранение SHA256, отзыв и проверка purpose.
Приём и назначение — короткие SQLite-транзакции до ответа; site+UUID UNIQUE и JCS fingerprint.
Назначения имеют уникальное активное право, UUID/generation/epoch; offer/accept/renew,
replay без повторного продления, reconnect и истечение реализованы во внутреннем API ядра.
Smooth weighted round robin, совместимость и FIFO, консервативный учёт занятых slots,
пороги ресурсов и устойчивый допуск. История/audit 30 дней, отдельные вечные tombstones.

Управление пока CLI при остановленном сервере. WSS/Node — этап 3, файлы/публикация — этап 4,
модели — этап 5, аккаунты/панель — этап 6, backup/restore/update — этап 7.
Результаты видео здесь ещё не создаются. Внутренние тестовые подключения не означают
проверку реальной работы Mac/Windows/Linux-обработчиков.

## Выполненные проверки

- Windows: `go test ./...`, `go vet ./...`.
- Linux amd64/Alpine в Docker: `go vet ./...`, `CGO_ENABLED=1 go test -race ./...`.
- Контракты: `python contracts/validate.py`; схемы, 29 HTTP operations/references,
  29 положительных, 9 отрицательных по форме, 7 семантически отрицательных примеров;
  11 трасс, 4 случая lease и 2 задержанных grant. Это проверка спецификации, отдельно от Go.
- 20 конкурентных приёмов одного UUID дают одну запись; два устройства — одно назначение.
- Повтор accept/renew не увеличивает expiry; чужое устройство/устаревший Fence отклоняются.
- Истечение offer не тратит лимит запусков; третья временная ошибка исполнения завершает FAILED.
- Соотношение весов 4:1 даёт 16:4 из 20 запусков при постоянном eligible backlog;
  сохраняется FIFO, несовместимая первая задача не блокирует совместимую следующую.
- Забронированный slot, CPU=80%, нестабильное снижение и недостаток диска блокируют новый offer.
- Cancel/release ждут stop/expiry; receipt не выдаётся при действующем праве, поздний результат отвергается.
- Токены разных purpose/сайтов изолированы, секрет не выдаётся в списке, revoke блокирует renewal.
- Обычный restart сохраняет epoch/право/дедупликацию; процессный crash после commit без Close
  сохраняет заявку; второй процесс не может открыть ту же БД.
- Очистка терминальных jobs/assignments/renewals сохраняет tombstones и не трогает активную очередь.
- Собран runtime-образ, проверена Compose-конфигурация, HTTP стенд проверил restart и replay.

## Замеры

Стенд — компьютер владельца с Windows, Docker Desktop/Linux amd64, Go 1.27.0.
Контейнер ограничен 256 MiB/1 CPU. HTTP нагрузка — 10 сайтов, 20 зарегистрированных offline
устройств и 2000 небольших JobRequest из fixtures, без файлов и WSS; последовательный клиент
создаёт отдельные HTTP-соединения. Скрипт [load-docker.ps1](../../scripts/load-docker.ps1)
создаёт свой временный том и удаляет только свои ресурсы.

| Показатель | Измерение |
| --- | --- |
| Docker memory до нагрузки | 7.766 MiB |
| Docker memory после 2000 заявок | 15.36 MiB |
| memory.peak cgroup, включая cache | 22.98 MiB |
| CPU time контейнера при приёме 2000 заявок | 3.962 с |
| Время последовательного HTTP приёма | 50.539 с |
| Скорость этого стенда | 39.57 заявки/с |
| Исполняемый Linux-файл, без debug symbols | 12 304 544 байта (~11.73 MiB) |
| Docker image inspect.Size | 9 436 381 байт (~9.00 MiB) |
| Docker image ls Size (общий показатель store) | 32.1 MB |
| Windows-проверка ядра с 2000 jobs/10 sites/20 sessions | peak working set 70.02 MiB |

Docker inspect.Size — показатель image store, а не RAM или размер всех распакованных файлов;
на этом Docker backend он отличается от суммы размеров файлов. Build/test images и caches
требуют отдельного дискового места и не являются runtime-образом.
Windows-профиль включает подготовку тестов и паузу наблюдения 3 с: CPU 1.719 с, wall 8.536 с.
Его working set нельзя напрямую сравнивать с Linux Docker memory/cgroup cache.

Контейнерный restart проверил сохранение всех 2000 заявок, повтор исходного POST вернул
200 QUEUED, а не создал новую запись. Ограничение 256 MiB подходит этому стенду.
Большие manifests, реальные WSS-соединения, публикации и будущая панель потребуют новых
замеров; данные не являются прогнозом VPS и не измеряют скорость перекодирования видео.
