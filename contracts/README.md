# Контракт диспетчера и обработчиков — 2.0

Дата: 2026-10-13. Завершён проект контракта этапа 1; endpoints и сообщения здесь
предназначены для реализации, работающего сервиса пока нет.
Технические значения по умолчанию можно менять в настройках без изменения смысла протокола.

- [Нормативный протокол](v2/protocol.md): HTTP, WSS, файлы, авторизация и миграция v1.
- [Состояния и правила исполнения](v2/states.md).
- [OpenAPI 3.1](v2/openapi.json): HTTP сайта и общей панели.
- [JSON Schema 2020-12](v2/protocol.schema.json): DTO, варианты операций и WSS-сообщения.
- [Настройки планировщика/сроков](v2/defaults.json).
- [Сценарии переходов](fixtures/scenarios.json), положительные и отрицательные примеры
  в fixtures/valid и fixtures/invalid.
- [Задачи агента бэкенда/фронтенда](../docs/plan/site-integration-stage1.md).

Проверка контрактных артефактов (Python 3, jsonschema):

```powershell
python contracts/validate.py
```

Генератор `build_contracts.py` — инструмент разработки схем/примеров, а не язык
диспетчера или обработчика. Изменять схемы в генераторе, затем выполнять
`python contracts/build_contracts.py` и проверку. Генерация детерминированная.
Зависимость валидатора закреплена в requirements.txt. На текущей машине она уже есть;
для новой среды установить в отдельное Python-окружение.

JSON Schema проверяет форму, но не доступ к объектам, срок исполнения, допустимые
переходы, достоверность нагрузки или содержимое HLS. Эти инварианты перечислены
в нормативных документах и отдельном валидаторе примеров. Прохождение проверок схем
не означает, что production-исполнение уже проверено.

OpenAPI использует относительные `$ref` на protocol.schema.json; при передаче агенту
передавать каталог contracts целиком. `*.example.invalid` / `worker.invalid` —
тестовые идентификаторы, не адреса для подключения и не источники реальных секретов.

Стандарты: [JSON Schema](https://json-schema.org/draft/2020-12),
[HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110),
[SQLite transactions](https://www.sqlite.org/lang_transaction.html).
