# Протокол 2.0: сайт, диспетчер и устройства

Дата: 2026-10-13. Нормативная спецификация для реализации этапов 2–7.
Схемы: protocol.schema.json; HTTP: openapi.json; переходы: states.md.
Здесь выбраны технические детали по согласованным требованиям, не новые ограничения
числа задач сайтов. Версия схем не утверждает наличие живого API.

## 1. Версии, идентичность и авторизация

Новый сайт API: `/api/v2/site/*`. Новый admin API: `/api/v2/admin/*`.
WSS: `/api/v2/device/connect`, HTTP Upgrade с `Authorization: Bearer <device-token>`;
процесс Node может передать заголовок, браузер здесь не используется.
Все сообщения WSS имеют protocolVersion=2.0, UUID messageId, type, direction, body.
Неизвестная major/minor-версия отклоняется до назначения, неизвестный тип — protocol.error.
Не передавать токены в query URL, журналы или payload модели.

Сайт определяется токеном, а не переданным siteId/Origin/адресом. Ключ уникальности
задачи — аутентифицированный сайт + id из JobRequest. Этот id — UUID внешней попытки
сайта, не ID видео/урока. clientReference помогает сайту связать работу со своей записью,
но не даёт права доступа и не содержит пользовательский текст.
UUID задания и source.revision канонизируются в нижний регистр до fingerprint/сохранения;
разный регистр написания UUID не создаёт новую работу.

Внутри задачи каждое назначение имеет новый assignmentId и возрастающую generation;
dispatcherEpoch меняется при восстановлении старого бэкапа, но не обычном restart.
Fence=(assignmentId,generation,dispatcherEpoch) передаётся во всех сообщениях/результатах.
Токен устройства даёт доступ только к его назначениям. Сайт видит только свои задачи.

Дедупликация охватывает версии API: нельзя принять один ID как две задачи через v1/v2.
При совпадающем ID и другом неизменяемом содержимом → HTTP409 IDEMPOTENCY_CONFLICT.
Повтор точно той же заявки → текущее состояние, без новой очереди/назначения.
Смысл заявки включает type, source revision/objects/hash/role, params, продуктовые пределы
и clientReference. Временные URL не входят: в v2 они передаются отдельно.
Проверяемый fingerprint: SHA-256 канонического JSON RFC8785 (JCS), а не строка исходного тела.
Историю удаляем через 30 дней, минимальную запись ID/fingerprint/терминального статуса
автоматически не удаляем. На tombstone GET → HTTP410 JOB_HISTORY_EXPIRED,
POST того же ID → тот же окончательный отказ 410, никогда не новая работа.

## 2. Приём и возможности

GET capabilities возвращает разрешённые сайту операции, языки распознавания,
направления перевода, autodetect, форматы, поддержанные политики видео и availability.
Это снимок возможностей реально установленных исполнителей, не обещание последующего допуска.
Права и поддержка проверяются при POST и при назначении.

Не объединять языки разных несовместимых устройств в выдуманный полный конвейер:
availability ONLINE означает наличие хотя бы одного устройства, способного выполнить
соответствующий вариант операции. При приёме проверяется конкретный запрос.
Для transcode дополнительные языки могут дать частичный результат; основная видеополитика
обязательна. Несовместимый/отсутствующий основной исполнитель → REJECTED до приёма.
Устройство с нужными возможностями временно offline → допускается QUEUED;
сайт может запросить release, если решит использовать резерв.

POST jobs принимает JobRequest, сохраняет до ответа: HTTP202 QUEUED для новой заявки,
HTTP200 для повтора или сохранённого REJECTED (с error). Rejected ID остаётся rejected;
для новой попытки после изменения условий сайт создаёт новый UUID.
Некорректная форма → 400; неизвестный токен401; запрещённый сайт403; тело слишком велико413;
конфликт ID409. 429 — инфраструктурный предел запросов, не квота очереди сайта.
Сетевой сбой/5xx после передачи всегда неопределённость: тот же ID/опрос, не дубль.
После неопределённости 401/403/404/410 тоже не доказывают, что исполнения не было.

GET jobs/{id} возвращает JobView. progress может быть null, если инструмент не даёт
оценки. updatedAt — любое изменение, lastProgressAt — подтверждённое продвижение,
а не просто heartbeat. queueDelayed выставляется после 600 с ожидания без старта.
Прогресс может начать заново при новой generation, это не регресс одной попытки.
GET jobs поддерживает непрозрачный cursor и limit≤100 (по умолчанию20), включает
actionable=true для ожидающих действий сайта. Список содержит полные JobView:
artifact обязателен для AWAITING_PUBLICATION/PUBLISHING/SUCCEEDED/PARTIAL,
для остальных состояний необязателен. Лимит тела8МБ, при больших результатах limit уменьшать
и получать каждую задачу отдельно. Не пропускать ожидающие actions при фильтрации истории.

## 3. Операции и неизменяемый профиль

| type | Обязательный результат | Дополнительное |
| --- | --- | --- |
| media.transcode | HLS, profile | subtitles: распознавание + отдельные переведённые дорожки |
| media.transcribe | UTF-8 текст оригинала | Ничего; без таймкодов/перевода/говорящих |
| media.subtitles | Отдельные дорожки для существующего видео | Оригинал и выбранные языки, без пересжатия видео |

subtitles.includeOriginal=true или непустой targetLanguages обязательны семантически.
Одинаковый язык оригинала/перевода даёт одну дорожку каждого формата, не дубли.
sourceLanguage=auto запускает определение. Если confidence недостаточен/смешанная речь
не поддержана выбранным исполнителем → LANGUAGE_UNDETERMINED и предложение ручного языка;
не выдавать заведомо неверный язык. Смешанные языки разрешены только при заявленной
поддержке исполнителя; первая версия может вернуть явную дополнительную ошибку.

profile содержит полный снимок Settings → Media: qualities, сегмент, x264 preset/CRF,
AAC bitrate/channels, цели битрейта всех качеств, допуск passthrough, allowUpscale=false,
policyVersion=site-hls-2026-10-01. Инфраструктурные concurrentJobs, CPU/RAM, binary paths
на сайт API не передаются. maxDurationSeconds/maxOutputBytes — продуктовые пределы файла,
не право управлять ресурсами устройства.

X264_EXACT сохраняет libx264 preset/CRF (0 применяется как1) и правила сайта; для кодирования
требует x264. HARDWARE_ALLOWED разрешает аппаратный исполнитель только при опубликованном
проверенном mapping этого профиля и политики. Нельзя трактовать CRF как равный CQ другого
энкодера. Пока mapping не проверен, устройство не объявляет HARDWARE_ALLOWED.
Кодек, битрейт, разрешение, звук и профиль не меняются молча ради ускорения.

COPY/ENCODE/SKIP_UPSCALE повторяют существующие правила VideoPackagingPolicy:
совместимость H.264/yuv420p/профиля/CFR/ключевых кадров/поворота/битрейта,
нет апскейла, AAC копируется только при соблюдении лимитов. Если все выбранные качества
выше источника, одна дорожка фактического разрешения не выше потолка.
Manifest содержит фактические width/height/bandwidth/mode и плейлисты, не обещанные ярлыки.

Повтор дополнительного шага после опубликованного видео — новый media.subtitles ID
с source.role=PUBLISHED_MEDIA; сайт сохраняет связь с тем же видео. Для HLS-source
передаётся список SourcePart, обработчик скачивает авторизованные части и локально
переписывает ссылки, не ходит по произвольным адресам исходного m3u8.
FILE-source.sha256 — хеш файла; HLS-source.sha256 — JCS-хеш отсортированных SourcePart,
bytes — сумма размеров уникальных частей. objectName — входной файл/мастер, revision
неизменяемая версия сайта; замена объекта требует новой задачи.

## 4. Канал устройств и назначение

device.hello содержит ОС/архитектуру/память/ускорение/исполнители, usage и локальные
активные Fence. Проверить deviceId по токену. session.welcome даёт sessionId/epoch/тайминги;
предыдущая сессия устройства закрывается, её сообщения больше не принимаются.
Только одной сессии разрешено обновлять назначение устройства.
Интервалы настраиваются и сообщаются в session.welcome; leaseSeconds должен быть больше
heartbeatSeconds + stopSafetySeconds. Числа 15/120/5 ниже — значения по умолчанию,
формулы используют согласованные интервалы, а не жёстко заданные константы.

Каждые15с: device.heartbeat с ресурсами и актуальными возможностями; для каждой активной
работы job.status с renewalId, этапом, activitySequence, progress и steps.
Heartbeat без job.status не продлевает право конкретной работы.
Информация устройства помогает планированию, но не является доверенным доказательством
качества/целостности результата. Ограничение ресурсов дополнительно проверяется локально.

Назначение двумя фазами:

1. Диспетчер атомарно резервирует QUEUED → ASSIGNED, записывает новый Fence и отправляет
   job.offer. Это ещё не право скачать/обрабатывать. Offer ждёт ack10с.
2. Устройство проверяет возможности/место/лимиты и отправляет job.accept либо decline.
3. После durable accept диспетчер переводит RUNNING и отвечает lease.granted
   с renewalId=messageId accept и expiresAt=время принятия+120с.
4. Обработчик начинает только после lease.granted. Потерянный grant не разрешает
   диспетчеру мгновенно отдать работу другому: записанное право действует до expiry.
5. job.status обновляет lease только для текущего Fence и неповторного renewalId.
   Дубликат получает исходный grant, не новое продление. Старые/истёкшие renewals отклоняются.

Обработчик запоминает момент отправки accept/status локальными монотонными часами;
его deadline не позже sentAt+120с−5с. Диспетчер deadline=receivedAt+120с.
Запоздалый grant не продлевает локальную работу от момента получения; требуется ещё
живой локальный deadline. Проверять также прошедшее реальное время после сна и право
перед запуском процесса/upload. Не полагаться на синхронность wall-clock разных компьютеров.
При сомнении остановить и сверить, нельзя воскресить истёкшую попытку.

Через120с без подтверждённого renewal диспетчер инвалидирует старый Fence и ставит QUEUED
с новым назначением позднее. Время последнего сообщения устройства без task-renewal
не отменяет истечение. После reconnect device.hello.active сверяется: действующим
попыткам возобновляется обмен, остальные получают stop, никаких запусков из папок вслепую.
Приложение обязано иметь независимый контроль остановки дерева процессов; OS-зависание
может дать краткий overlap вычислений, но право и публикуемый результат только одни.

job.failed временный → до3 запусков исполнителя всего, затем FAILED. Перед новым запуском
старая попытка остановлена/истекла. Неподдерживаемый файл/профиль → permanent без повторов.
Ошибка дополнительного шага оформляется в Manifest.steps, не job.failed основного видео.

## 5. Ссылки без callback и доставка результата

Сервис не принимает произвольный callback URL сайта. Сайт регулярно (5с + backoff)
опрашивает свою задачу и GET jobs/{id}/transfers. Даже когда файлов нет, QUEUED не требует
скачивания. Потерянные/отозванные ссылки обновляются через этот же долговечный обмен.

1. Обработчик job.source.request; диспетчер создаёт TransferRequest SOURCE с UUID,
   текущим Fence и sourceRevision; повтор возвращает существующий открытый запрос.
2. Сайт видит запрос, проверяет владение/ревизию, выдаёт GET для FILE или HLS частей
   и POST transfer-grants. requestId/fence/pages сохраняются атомарно.
3. Диспетчер проверяет fence, маршрут токена/владение и передаёт grant устройству.
   FILE link.path="source"; HLS link.path равен SourcePart.path. Назначения объектов
   должны точно совпадать с заявленным source, не arbitrary URL.
4. После обработки job.artifact.propose содержит Artifact с неизменяемым ID,
   Manifest и manifestSha256=SHA256(JCS(manifest)). Диспетчер сохраняет до ответа.
5. Сайт получает TransferRequest UPLOAD и выдаёт PUT на каждый путь; по256 ссылок
   на страницу. requestId+page идемпотентны, refresh может менять URL/expiry/headers,
   но не path/objectName/метод. Все страницы — один неизменяемый набор объектов.
6. Staging-prefix минимум `jobs/<site-id>/<job-id>/<epoch>/<generation>/<assignment-id>/`.
   Сайт выбирает абсолютные objectName; обработчик выбирает только безопасные относительные
   path из манифеста, не произвольные назначения. Каждая grant page должна быть полна,
   дубликаты/path traversal/лишние пути отклоняются. Partial grant не разрешает commit.
7. Обработчик загружает файлы напрямую, retries после первой попытки3 с паузами5/15/45с.
   Продлевает право во время ожидания/grants/upload. После job.upload.complete
   диспетчер фиксирует AWAITING_PUBLICATION и артефакт, **исполнение закрывается**;
   дальнейший heartbeat не нужен для этого задания, публикация не зависит от жизни Mac.
8. Ошибка URL403/expiry → свежие ссылки через transfers, а не пересоздание медиапакета.
   Повтор complete с тем же artifactId/hash идемпотентен. Другой hash в той же попытке
   → ARTIFACT_CONFLICT; другая попытка → STALE_ASSIGNMENT.

Metadata request/WSS frame≤8МБ,≤10000 файлов, URL≤16КБ; grant page≤256.
Для HTTP такие тела ограничиваются во время чтения; лимиты — защита памяти,
не количество заданий сайта. Path case-sensitive, уникален, ASCII без обратных слешей,
.., абсолютных путей или URL. Повторные языки/плейлисты не дублируются.
URL TLS обязателен вне явно включённого LAN/localhost режима. Разрешённые storage origins
задаёт владелец у сайта; проверять destination после DNS, запрещать редиректы и произвольный
доступ к локальным/служебным адресам. Частный S3 endpoint возможен только как явное разрешение.
GET/PUT headers из grant ограничены нужными storage-заголовками, не допускаются cookies/
Authorization к произвольному чужому хосту.

## 6. Проверка и фиксация публикации

AWAITING_PUBLICATION сообщает actionable=true и Artifact. Сайт проверяет:
существование объектов, фактические sizes/checksums, полный состав и безопасные ссылки m3u8,
формат текста/субтитров, факт успешного основного шага. S3 ETag не считается SHA256.
Hash подтвердить storage checksum при гарантиях провайдера либо чтением объекта;
плейлисты читать/разбирать. Результаты не становятся READY только по ответу диспетчера.

Затем POST publication-claim с новым claimId и точными fence/artifact/hash.
Если предварительная проверка окончательно неудачна, сайт также сначала получает claim,
затем сообщает REJECTED: это закрепляет именно проверенную попытку и исключает гонку отмены.
Диспетчер атомарно проверяет актуальность и ставит PUBLISHING: артефакт закреплён
для решения сайта. Повтор того же claim возвращает тот же результат; другое содержимое409.
Во время PUBLISHING нельзя отменить/переназначить/выдать release: 409 PUBLICATION_IN_PROGRESS.
Claim **не истекает автоматически**: неопределённый commit сайта нельзя заменять новой
обработкой. При падении сайт восстанавливает claim из своей БД и доводит решение до конца.

Сайт копирует staging в свой окончательный prefix с новым publicationId, на который
обработчик НИКОГДА не получал PUT. Сравнивает хеши уже скопированных объектов, сохраняет
привязку к видео/дорожкам и READY в локальной транзакции с проверкой актуальной ревизии
загрузки. Одновременно сохраняет outbox PublicationDecision PUBLISHED.
Поздняя перезапись staging по старой URL не меняет опубликованные объекты.
После публикации нельзя DELETE staging раньше copy/проверок; cleanup в повторяемом outbox.

POST publication-decision с claimId/id/hash/fence/publicationId завершает SUCCEEDED
или PARTIAL по steps. Ответ200 PublicationAck означает durable фиксацию, повтор после
потери ответа отдаёт то же. Если сайт ещё не публиковал и проверка окончательно неудачна,
decision=REJECTED с причиной завершает FAILED. Проверку временных сбоев повторять3 раза
до rejection; при недоступном storage не публиковать ложную ошибку по одному HEAD.
Если READY уже сохранён, сайт никогда не посылает REJECTED; повторяет PUBLISHED из outbox.

Нет распределённой транзакции между БД сайта и диспетчером. Claim + outbox + immutable
final objects исключают подмену попытки, допускают временное расхождение статуса,
которое устраняется идемпотентным повтором. Общая недоступность сайта может оставить
PUBLISHING до сверки; нельзя автоматически пересоздать эту задачу только по таймеру.

Получив терминальный исход, устройство очищает рабочие файлы; если оно offline,
сверяет по reconnect и очищает. После upload.complete без ответа локальные результаты
сохраняются до reconcile, не считается успехом истечение аренды.

## 7. Частичный успех, удаление и отмена

media.transcode: основной шаг video обязателен. Дополнительные дорожки FAILED/SKIPPED
с причиной → PARTIAL после успешной публикации video и готовых дорожек, сайт показывает
причины/ручной ввод. Ошибка video → FAILED и очистка только этого непубликуемого upload.
media.transcribe: transcript обязателен. media.subtitles: если нет ни одной готовой дорожки
→ FAILED операции, исходное опубликованное видео остаётся; часть языков готова → PARTIAL.
Нет переводов для языка оригинала → копия дорожки, не бессмысленный запуск перевода.

role UPLOAD: исходник сайта удаляется после primary success/окончательного primary fail
или отмены, но не до завершения повторов/публикации. role PUBLISHED_MEDIA: существующее
аудио/видео не удаляется из-за ошибки расшифровки/subtitles. Сайт управляет очисткой;
диспетчер/устройство не имеют полномочий удалить источник из S3.
Автоочистка файлов даты работает только с состояниями, не удаляет активное ожидание
публикации. Orphan24ч — после доказанного отсутствия действующего назначения и сверки;
когда диспетчер недоступен, неизвестные файлы не удалять вслепую.

POST cancel с requestId/reason: queued → CANCELLED; assigned без права → CANCELLED;
running → CANCELLING, job.stop, ждать stopped либо истечения lease. Затем CANCELLED,
новых назначений нет. Повтор запроса возвращает текущее состояние. Повтор с другим смыслом409.
Терминальный успех не превращается в cancelled; сайт отдельно удаляет опубликованное видео.
На PUBLISHING отмена не завершает работу: нужен локальный исход сайта.

POST release — не отмена пользователем, а отказ от внешнего исполнения в пользу резерва.
QUEUED/ASSIGNED → RELEASED сразу, RUNNING → RELEASING с той же остановкой/expiry,
AWAITING_PUBLICATION → RELEASED только если claim не выдан. releaseReceipt выдаётся
только после завершённого отсечения ВСЕХ внешних прав; task terminal forever.
Сайт сохраняет receipt, переключает собственную задачу на SERVER в транзакции,
исключает повторный запуск локальной попытки. PUBLISHING/успех →409, release не разрешён.
Недоступность диспетчера не равна receipt. Повторяем requestId и ждём подтверждения,
не запускаем резерв вслепую, даже если две минуты уже прошли.

## 8. Общая панель и команды

AdminSession — HttpOnly Secure SameSite cookie, CSRF token для mutations, login rate limit.
Владелец создаёт аккаунты/устройства и меняет глобальные настройки. Оператор управляет
очередью/устройствами/моделями, sites только с manageSites; никогда accounts/tokens-device.
Пароли хешируются подходящим password KDF, не SHA256; токены — случайные≥256бит,
хранится проверочный хеш, purpose и principal. revoke инвалидирует сессии/новые назначения,
но не доказывает прекращение уже работающего процесса: ждать stop/lease для передачи.

Создание, список и обновление site/device/account и выдача токенов описаны в OpenAPI.
В первой версии записи отключают через enabled; удаление учётных записей не предусмотрено.
PUT требует If-Match revision,
иначе428/409; нельзя удалить/понизить последнего владельца. Создание аккаунта требует password,
обновление использует AdminAccountUpdate: отсутствие password сохраняет пароль,
пустой password отклоняется.
TokenCreate requestId: показываем plaintext ровно при первом успешном201. После потерянного
ответа повтор возвращает409 TOKEN_SECRET_ALREADY_ISSUED; владелец отзывает tokenId из списка
и выдаёт новый, не хранить plaintext ради replay. GET /api/v2/admin/tokens возвращает
только метаданные для revoke, без секрета.

device commands MODEL_INSTALL/ACTIVATE/DELETE/CONFIGURE имеют устойчивый requestId.
Диспетчер durable enqueue →202 MutationAck означает «принято», не «применено».
Поле applied этого подтверждения относится к записи команды в диспетчере.
Панель получает результат GET commands/{requestId}; device.command.result сохраняется,
CommandView возвращает PENDING до начала исполнения, затем RUNNING/SUCCEEDED/FAILED.
повтор команды не повторяет скачивание/переустановку. Смена workDirectory ждёт отсутствия
активных работ; offline команда остаётся pending. Удаление активной модели отклоняется409.
Адрес загрузки/версия/хеш берутся из каталога, сайт не задаёт shell command/downloadUrl.
Проверка модели, активирование и сообщение возможностей раздельны: скачанное ≠ работающее.

Модельный каталог содержит provenance/license/version, ОС/архитектуру/ускоритель,
RAM/VRAM/downloadBytes, хеш и проверенные языки/направления. Это данные подготовленных
моделей, не попытка автоматически угадать все возможности произвольных весов.
Вне каталога модель регистрируется владельцем после отдельной проверки.

## 9. Миграция существующего клиента v1

Текущие `/api/site/operations`, `/api/site/jobs`, `/api/site/jobs/{id}` имеют фиксированные
outputs и ZIP-transcode, без publication. Не переименовывать ответы молча в v2.
Начальная поставка диспетчера реализует v2; legacy endpoints дают понятный отказ
до приёма PROTOCOL_UPGRADE_REQUIRED (operations:403; jobs:200 REJECTED с исходным id/code).
Новые задачи через legacy не исполняются. Это явная миграция, не заявление готовой поддержки v1.
После неопределённой старой попытки даже такой отказ не разрешает локальный дубль.
При наличии незавершённых legacy-работ сначала сверить/закрыть их на старом исполнителе.

Бэкенд сайта обновляет клиент/схемы по v2, переносит продуктовый видеопуть в очередь,
а существующую политику видео и защиту от неопределённости сохраняет.
Сайт подключается EXTERNAL только после проверки версии/возможностей; неверная версия
отображается как PROTOCOL_ERROR и не принимает видимость успешного подключения.
Код legacy клиента можно переиспользовать, но body/статусы/лимиты/poller transfer actions
потребуют изменения. Runtime/VPS проверяется отдельно перед production.

Хеширование канонического JSON: [RFC8785](https://www.rfc-editor.org/rfc/rfc8785).
HTTP: [RFC9110](https://www.rfc-editor.org/rfc/rfc9110).

## Подтверждение терминальных сообщений устройства (этап 3)

`job.failed`, `job.stopped`, `job.decline` сохраняются обработчиком в outbox и
повторяются с прежним `messageId`/телом до `protocol.ack {replyTo}`.
Диспетчер фиксирует дедупликацию и изменение задания одной транзакцией до ack.
Дедупликация ограничена устройством, проверяется текущая сессия/токен; одинаковый ID
с иным содержимым даёт IDEMPOTENCY_CONFLICT. Запись переживает смену соединения/restart.
После срока истории запись можно удалить: fence старой попытки всё равно не даёт
изменить новое назначение. STALE_ASSIGNMENT/LEASE_EXPIRED прекращают повтор terminal.
Повтор accept/status использует существующий renewalId и возвращает прежний grant,
никогда не продлевает срок относительно времени повторного запроса.
