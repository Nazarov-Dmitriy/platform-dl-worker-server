# Установка worker-server и переезд на другой VPS

Комплект для Linux amd64: готовые образы диспетчера и TLS-прокси, Compose,
установщик и перенос состояния. На VPS нужны Docker Engine с Compose v2,
Python 3.9+ и OpenSSL. Go, Node.js, FFmpeg и модели диспетчеру не нужны.
Mac/Windows подключаются как отдельные обработчики.

## Первый запуск

Распакуйте архив релиза в отдельную папку, например `/tmp/worker-release`.
Положите на сервер сертификат (полную PEM-цепочку) и незашифрованный PEM-ключ.
Сертификат должен соответствовать вашему IP или DNS-имени. Затем одна команда:

```sh
sudo bash /tmp/worker-release/install.sh \
  --host 194.5.79.198 --cert /root/fullchain.pem --key /root/privkey.pem
```

Панель: `https://194.5.79.198:8090/panel/`.
Адрес устройства: `wss://194.5.79.198:8090/api/v2/device/connect`.
В настройках сайта адрес сервиса: `https://194.5.79.198:8090`.
Диспетчер HTTP наружу не публикуется, порт TLS — 8090. Существующий Nginx сайта,
порты 80/443, настройки бэкенда и правила firewall установщик не изменяет.
Разрешите входящий TCP 8090 в firewall VPS и панели провайдера.

Логин владельца — `owner`. Первоначальный пароль лежит только в
`/opt/worker-server/initial-owner-password` с правами 600. Посмотреть:

```sh
sudo cat /opt/worker-server/initial-owner-password
```

Не отправляйте пароль, приватный ключ или архив переезда в Git/публичные сообщения.
Сайт и каждое устройство получают отдельные токены через панель диспетчера.

Опции: `--dir /opt/worker-server`, `--port 8090`, `--owner-login owner`.
`--listen-ip 127.0.0.1` подходит для изолированной проверки/SSH-туннеля.
Для сертификата своего удостоверяющего центра добавьте `--ca /root/ca.pem`;
этот CA также должен быть доверенным на Mac/Windows и бэкенде сайта.
Проверка сертификата не отключается. Установщик не выпускает и не продлевает
сертификаты. Для замены сертификата повторите ту же команду с новыми файлами.

Повторная установка той же версии сохраняет базу, владельца и токены.
Коротко перезапускается только собственный TLS-прокси; действующий диспетчер
не сбрасывается. Произвольная смена образа поверх существующей базы запрещена:
для обновления сначала обслуживание, снимок SQLite и согласованный путь миграции.

## Переезд

1. В панели включите обслуживание и дождитесь завершения назначенных работ.
2. Выполните на старом VPS:

   ```sh
   sudo bash /opt/worker-server/export.sh /root/worker-move.tgz
   ```

   Команда остановит экземпляр и сохранит согласованные базу, токены, настройки,
   сертификаты, образы и установщик. Старый экземпляр останется остановленным.
3. Перенесите архив по SSH на новый сервер, распакуйте **с sudo** в
   `/opt/worker-server` (сохраняются числовые UID владельцев файлов).
4. Запустите тот же установщик:

   ```sh
   sudo bash /opt/worker-server/install.sh \
     --host НОВЫЙ_IP --cert /root/new-fullchain.pem --key /root/new-privkey.pem
   ```

   При сохранённом DNS-имени можно использовать прежний действующий сертификат:
   `--cert /opt/worker-server/tls/fullchain.pem --key /opt/worker-server/tls/privkey.pem`.
   Для частного CA снова передайте `--ca /opt/worker-server/tls/ca.pem`.
5. Откройте порт у нового провайдера, проверьте панель, подключите устройства,
   обновите IP в их адресе (или DNS), затем выключите обслуживание в панели.

Две копии одной базы одновременно не запускайте. Экспорт — перенос полного
остановленного состояния, а не восстановление произвольного старого снимка.
Для отката к старому снимку используйте штатную `restore` с новой epoch.
На старом VPS не запускайте экземпляр после начала обработки новым сервером.
Архив содержит секреты; храните его приватно и удалите временные копии после переезда.

## Проверка и управление

```sh
cd /opt/worker-server
sudo docker compose ps
sudo docker compose logs --tail=50
sudo docker compose stop
sudo docker compose up -d
```

В архиве `release.env` фиксирует тег и отпечатки готовых образов, `SHA256SUMS` — хеши
файлов поставки. Перед установкой распакованного релиза: `sha256sum -c SHA256SUMS`.
Для исходников вместо готового архива можно передать `--image <версионированный-образ>`;
тогда образ скачивается из реестра (при private-реестре сначала `docker login`).

Запуск диспетчера не включает EXTERNAL на сайте. Сквозная проверка с реальным
обработчиком и тестовым файлом нужна перед переключением рабочих загрузок.

## Конфигурация комплекта

Установщик создаёт собственный `.env`, без копирования ENV бэкенда сайта:

- `DISPATCHER_IMAGE`: источник `release.env` или `--image`; обязателен, тег версии,
  `latest` не принимается. В готовом архиве образ уже приложен, реестр не требуется.
- `PUBLIC_HOST`: источник `--host`, обязателен; IP/DNS без схемы и порта. Используется
  для проверки сертификата и готовности, не подставляется в Nginx как исполняемый текст.
- `PUBLIC_PORT`: источник `--port`, по умолчанию 8090; диапазон 1024–65535.
- `LISTEN_IP`: источник `--listen-ip`, по умолчанию `0.0.0.0`; IPv4-интерфейс публикации.
- `OWNER_LOGIN`: источник `--owner-login`, по умолчанию owner; при повторной установке
  сохраняется прежний логин. Пароль в `.env` не записывается.

`release.env` дополнительно содержит `DISPATCHER_IMAGE_FINGERPRINT` и
`TLS_IMAGE_FINGERPRINT`: хеши слоёв и параметров запуска обоих образов. Они проверяются
после загрузки архива и не зависят от различий classic/containerd image store.

Для сборки новой поставки из исходников: `bash deploy/standalone/package.sh`.
Результат появляется в `bin/releases/` (не коммитится). Linux-тесты с race detector
запускаются до упаковки. `.github/workflows/release.yml` делает то же на GitHub,
проверяет установку/переезд и прикладывает архив к релизу по тегу `worker-v*`;
ручной запуск workflow сохраняет архив как Actions artifact. На VPS исходники
и инструменты сборки не переносятся.
